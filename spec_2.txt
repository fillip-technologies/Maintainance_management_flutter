
Maintenance module
Detailed documentation — hierarchy, roles, flow states, and table schema
1. Hierarchy model
The platform hierarchy is fixed: Platform → Company → Client → Vertical. Inside the hardware/CCTV vertical, the zone structure below the client is where all the flexibility lives.

Figure 1. Platform-level hierarchy — fixed spine that every vertical plugs into.
The zone layer is a single self-referencing table: every zone row has an optional parent_zone_id pointing to another row in the same table. This is what makes the hierarchy “vertical” in the sense you described — unlimited depth, no schema change needed to add a level.
A client can have any number of top-level zones (Zone A, Zone B, Zone C…).
Any zone can have any number of sub-zones, and those sub-zones can have their own sub-zones, indefinitely.
Devices (cameras, etc.) attach to whichever zone level is relevant — directly under a top-level zone, or several levels deep.
Each zone, at any depth, can have its own incharge and staff, independent of its parent zone’s staff.

Figure 2. Example: two top-level zones, one with a sub-zone, each with independent staff and devices.
Practically, this means the exact scenario you described — install cameras in the zoo, assign one admin and one staff, then later add a second zone with more cameras and a new incharge — is always the same three operations: create a zone row, attach devices to it, assign people to it. Nothing about the database or the permission model changes as you go deeper or wider.

Every transition writes a row to issue_status_history — nothing is overwritten in place, so the full timeline of an issue is always reconstructable after the fact.
Priority is a separate axis from status, set at creation and editable by the client admin: low → medium → high → critical. Priority does not gate status transitions — it only drives sorting, SLA timers, and notification urgency.
3.4 Daily status log
This is a snapshot, not a lifecycle — each entry is a new row per device per day, never edited afterward. Each entry is one of:
working — normal, no action needed
not_working — device is down; the UI can prompt “raise an issue for this?” to avoid a silent gap between a bad log and an actual ticket
needs_attention — partially working or showing early warning signs
The trend across days matters more than any single entry — e.g. three consecutive not_working entries auto-flags the device as faulty per section 3.2, even if nobody has raised a ticket yet.

6. Decisions to lock in before building
Cascading visibility — does a parent zone’s incharge see sub-zone data, or is client admin the only roll-up view?
Reassignment — can a zone incharge reassign a ticket to a different technician mid-flight, or only client admin/platform?
Auto-close window — how many days after resolved before an issue auto-closes if nobody disputes it?
Faulty threshold — how many consecutive not_working daily logs before a device auto-flags as faulty?
